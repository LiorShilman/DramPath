# ADR 0007: Phone-as-remote-controller — no pairing/auth, but reachable at a fixed address everywhere

## Status
Accepted.

## Context
DrumPath already has a standalone touch page (`/practice/touch`, and a second real HTML entry `touch.html` with its own PWA manifest) for practicing on a phone away from the desktop — deliberately no networking at all. Separately, the user wanted to use the phone to control the **desktop's** `VisualTrainerPage` session live — tapping drum pads on the phone instead of the desktop's keyboard while a graded exercise plays on the desktop screen. This requires two devices to talk to each other in real time, which a static SPA with no backend (ADR 0006 already established `server/drum-import-service/` as the one precedent for an optional local service) can't do on its own — a browser tab can be a WebSocket *client* but never a *server*.

Three transport options were considered: Bluetooth (rejected — Web Bluetooth is GATT/IoT-device-oriented, unsupported in Safari/iOS, and awkward for connecting two general-purpose computers), WebRTC peer-to-peer (rejected — adds signaling complexity for no real benefit when both devices are already on the same LAN), and a small local WebSocket relay server, same shape as `drum-import-service` (chosen, confirmed with the user).

`useVisualTrainer.ts`'s `handleHit(instrument, hitTimeMs)` was already 100% input-source-agnostic before this feature — its only caller was `useKeyboardDrums`. `hitTimeMs` must be `performance.now()`-comparable on the *desktop's own clock* (it feeds `clockOffsetMsRef`, computed from the desktop's own `AudioContext`); a phone's own timestamp would be on an unsynchronized clock.

**Revision (same day):** the first version of this feature stayed dev-time/LAN-only, reasoning that the deployed `https://shilmanlior2608.ddns.net:40000` site couldn't reach a relay running on `localhost`, and that testing the domain itself from inside the house had failed (diagnosed at the time as a NAT-hairpin limitation). The user pushed back based on years of using that same domain from inside the house across dozens of other projects — and was right: re-testing properly (`Invoke-WebRequest -SkipCertificateCheck` against the real domain) returned 200 OK from inside the house. The earlier failure was a PowerShell certificate-validation quirk in how the test was run, not a real network limitation. That correction removed the actual reason this stayed LAN-only, and the design below was revised accordingly.

## Decision
- **Separate service** (`server/remote-drum-relay/`, Python/FastAPI, mirrors `drum-import-service`'s shape) rather than folding a WebSocket route into the existing import service — unrelated concerns, same precedent for keeping local backends single-purpose.
- **Single global host, no pairing codes/rooms.** The relay holds at most one active "host" (desktop) connection; any "controller" (phone) that connects relays to whichever host is current. A deliberate v1 simplification for a personal, single-household tool, not a multi-tenant service. A second desktop tab connecting supersedes the first (WS close code `4001`) rather than leaving two hosts in an undefined state; the superseded tab does not auto-reconnect (which would otherwise fight the new one for the host slot).
- **No auth, trust the LAN.** Any device on the network can connect as a controller. `ALLOWED_ORIGIN`/CORS is kept for the health endpoint's consistency with the sibling service, but does not apply to WebSocket connections at all (Starlette's `CORSMiddleware` only processes HTTP) — it is not access control.
- **Receive-time stamping, not clock synchronization.** The desktop stamps its own `performance.now()` the instant a hit message arrives, rather than trusting any timestamp the phone might send. Network latency becomes the hit's timing error (tens of ms on a good LAN) — acceptable, comparable to normal human timing variance; NTP-style clock sync would be real complexity for no meaningful accuracy gain here.
- **Two parallel relay instances, selected by `location.protocol` — dev path unchanged, production path new.** In dev (`http://localhost:5173`), both sides connect exactly as originally built: desktop to its own `ws://localhost:8001`, phone to a manually-typed LAN `host:port`. Over the deployed `https://` site, both sides instead auto-connect to a second, always-on production instance at a **fixed address**, `wss://shilmanlior2608.ddns.net:40001` — no LAN IP, hostname, or pairing step, on either side, in that case. `src/lib/visual-trainer/remote-drum-protocol.ts`'s `buildProductionRelayWsUrl()` is the one place this address is defined; `useRemoteDrumInput`/`useRemoteDrumSender` each branch on `location.protocol` to pick dev vs. production, nothing else about their logic (status machine, supersede handling, retry policy) differs between the two.
- **Production TLS: the relay terminates it directly, on its own dedicated port — not proxied through IIS.** Considered and rejected an IIS/ARR reverse-proxy through DrumPath's existing port 40000 (ARR reverse-proxying is confirmed enabled server-wide, and already used this way by an unrelated sibling project) because it needs the **IIS-WebSockets** Windows feature, currently disabled on this machine, and turning it on requires an `iisreset` that briefly interrupts every other project on the shared IIS site — too much blast radius for this feature. Instead: `uvicorn --ssl-keyfile/--ssl-certfile` on its own port (40001, free in the already-router-forwarded 30000–45000 range), using a `cert.pem`/`key.pem` pair exported from the exact same Windows certificate (`CN=shilmanlior2608.ddns.net`, SHA1 `9f184b1be17de94755353c996d82a64293151e09`) IIS's bindings already share — the identical pattern `server/drum-import-service`'s sibling project `Photo2Print` already runs in production (`ecosystem.config.js`, PM2-managed, own cert files, own port). Doesn't touch IIS, ARR, or any other hosted project at all.
- **The production instance is PM2-managed but reboot-resurrection is a separate, not-yet-made decision.** `pm2 save` persists the process list; `pm2 startup` (auto-resurrect after a reboot) is not currently configured on this machine for *any* app (confirmed: the one existing saved PM2 dump only contains an unrelated project, no Scheduled Task registers `pm2 resurrect`) — deliberately left as a future, explicit, machine-wide choice rather than silently enabled as a side effect of this feature.

## Rationale
- Matches the existing local-service precedent (ADR 0006) instead of introducing a new pattern (Node/`ws`, a different language, a different run/deploy story) for what is, at its core, the same kind of thing: an optional, external process the PWA talks to.
- A pairing-code UX is real, user-visible complexity (generate a code, display it, type it, handle expiry) in exchange for a benefit — supporting multiple simultaneous unrelated households on one relay — this user's actual use case doesn't need, regardless of dev or production.
- Keeping `handleHit` itself completely unchanged means the entire existing grading/matching/scoring path (already tested, already correct) has zero new surface area to regress; the only new code is *what calls it*.
- The dedicated-port-and-own-TLS approach for production reuses an already-proven-in-production pattern on this exact machine (`Photo2Print`) instead of inventing a new one, and keeps this feature's entire footprint isolated to its own process/port/cert files — nothing shared with IIS or any other hosted project is touched, modified, or put at risk.

## Consequences
- Dev mode (`npm run dev -- --host` + the relay with `--host 0.0.0.0 --port 8001`, both plain HTTP/local) is unchanged from the original version of this ADR — still requires the desktop physically present and both processes running, still LAN-only, still manual IP entry on the phone.
- The production instance, once deployed, requires **no** physical/network proximity assumption at all — the fixed `wss://shilmanlior2608.ddns.net:40001` address works identically whether the phone is on the home network or away from it, same as every other project already deployed through this domain.
- Anyone who can reach that address could, in principle, connect a controller and send hits — accepted for a personal single-household tool (unchanged from the original decision); would need real auth/pairing before this could ever be multi-household or public.
- No queueing: a hit sent while no host is connected (or arriving faster than the desktop can process) is simply dropped, never buffered or replayed.
- Two relay processes now exist for this one feature (dev + production) rather than one — an accepted duplication in exchange for never touching the dev workflow while adding the production path, and for the production path being deployable/restartable independently of whether anyone is actively developing DrumPath at that moment.
