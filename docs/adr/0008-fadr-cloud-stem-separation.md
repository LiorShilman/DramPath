# ADR 0008: Optional Fadr cloud stem separation for drum-audio import

## Status
Accepted.

## Context
`drum-import-service` (ADR 0006) already turns 7 separated drum stem files (kick/snare/toms/hh/ride/crash/residual), which the user must already own, into a playable `InteractiveExercise` via its one synchronous `/api/v1/analyze` endpoint. The user subscribed to Fadr Plus (a paid third-party service, `api.fadr.com`) specifically because it can split a *full song* into those same per-instrument drum stems automatically, and asked for DrumPath to call that API directly instead of the user manually exporting stems from Fadr's own site and re-uploading them.

Fadr's own API documentation is explicit: the API key must never reach frontend/browser code ("protect it like it's your password"). DrumPath's frontend is a static SPA with no persistent Node backend and no existing pattern anywhere (`UserSettings`, `src/features/settings/`) for storing a user's personal API key — this would be a first-of-its-kind secret in the app.

ADR 0006's boundary is specifically about the **PWA** staying local-first/backend-free — it never asserted the *import service's own internals* must stay offline-capable; the service was already conceived as an external, optional process the PWA talks to. Routing stem separation through Fadr doesn't violate that boundary's letter, but it does change its accepted consequence.

## Decision
- **The Fadr integration lives entirely inside `drum-import-service`** (`app/fadr_client.py`, a new module), not the frontend and not a new service — the existing service is already the one place in this repo built to hold this kind of external-facing secret and orchestration, and `httpx` (already a dependency) covers the outbound HTTP need without adding a new library.
- **`FADR_API_KEY` is read server-side only, via `os.environ.get(...)`**, matching this service's existing config convention (`FFMPEG_BIN`, `ALLOWED_ORIGIN`) — never sent to, stored in, or requested from the browser. It is the first *required secret* (no default) this service holds, which justifies introducing `python-dotenv` + a gitignored `.env` specifically for local developer convenience around it.
- **Strictly additive and opt-in.** When `FADR_API_KEY` isn't configured, nothing about the existing manual-stem-upload flow changes at all. `GET /api/v1/health` gains a `fadrConfigured` boolean so the frontend can show/hide the new "upload a full song" option without guessing.
- **New endpoint, not a modified one.** `POST /api/v1/analyze-from-song` accepts one full-song file, orchestrates the Fadr pipeline (upload → main-stem separation → poll → locate the "drums" stem → re-separate it into individual instruments → poll → download), then hands the resulting local files to the **same, unmodified** `analyze_stems()` function `/api/v1/analyze` already calls — identical `AnalyzeResponse` contract, zero changes to the analysis pipeline, Zod validation, or `approveDrumImport`.
- **Still a single synchronous request/response, no job queue/SSE** — matches this service's existing "deliberately no job queue" stance (ADR 0006's own module docstring). The new endpoint simply blocks longer (Fadr's own multi-stage polling happens inside the request) rather than introducing a new async-progress mechanism.

## Rationale
- Keeping the key server-side-only is not a preference here, it's Fadr's own stated security requirement — there was no real alternative design to weigh against it.
- Reusing `analyze_stems()` unchanged means the entire existing, tested analysis pipeline and every downstream consumer (Zod contract, `approveDrumImport`, the preview/approve UI) has zero new surface area to regress — the only new code is *how the stem files get produced* before that function is called.
- A required secret with no sensible default is a genuinely different category from this service's existing optional/defaulted env vars, which is what justifies `.env`/dotenv here specifically rather than as a general policy change.

## Consequences
- Using the Fadr-backed import path means the user's audio leaves their machine and is processed by a third party — a real departure from `SPEC.md`'s local-first framing, accepted explicitly and only for this opt-in path; the manual-stem-upload path remains fully local as before.
- Each Fadr-backed import costs real money (Fadr Plus's API usage-based billing) and requires network access; the manual path remains free and offline-capable exactly as it always was.
- **Confirmed against a real account (2026-08-06): Fadr's "drum-stem" re-separation only ever returns 3 pieces — `kick`, `snare`, and one catch-all `drums-other` (hihat, toms, cymbals, everything else, all mixed into one file)**, not the individual hihat/toms/ride/crash breakdown its marketing implies. `fadr_client.py` maps `drums-other` to `analyze_stems`' own `residual` field (same catch-all a manual import uses) — it still gets onset detection, just no per-instrument or tom-pitch classification. **This means a Fadr-backed import is real but lower-fidelity than a manually-separated 7-stem import** — accepted as a real, permanent limitation of this API tier, not a bug to fix later. The tom-mixing code path in `fadr_client.py` is kept as forward-compatible dead code in case a future Fadr API version splits toms out separately.
- Several response shapes documented by Fadr's own docs prose turned out to be wrong when tested against a real account: every document is wrapped (`{"asset": {...}}`/`{"task": {...}}`, never bare), task completion is `status.complete` (a bool), not a `"done"`/`"failed"` string, and a completed task's own document never lists its resulting assets (`output.assets` stays `[]`) — they live on the *parent asset's* own `stems` array instead, as plain id strings each needing their own fetch. `fadr_client.py`'s module doc comment records the confirmed shapes; do not re-trust the docs prose over that comment if Fadr's API changes again.
